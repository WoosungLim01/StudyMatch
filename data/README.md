# StudyMatch — Sample Data

Synthetic-but-internally-consistent sample data for the StudyMatch spec (Penn State,
CMPSC 465 + MATH 230). Generated by [`generate_sample_data.py`](generate_sample_data.py)
(seeded, deterministic — rerun with `python generate_sample_data.py` to regenerate
into `sample/`). Nothing in `sample/` is real student data — but `studymatch.db`
is a real, live database that real people can be added to; see
["The intake webapp"](#the-intake-webapp-survey--admin) below.

This exists to give the rest of the build (schema design, API contracts, UI mocks,
matching-algorithm prototyping) real-shaped data to work against. The compatibility
math and group-formation logic in the script are the heuristic placeholders from the
spec, not a final algorithm — expect to replace both once real `group_feedback`
accumulates (spec §16–17).

**Matching scope**: compatibility is **personality similarity only** — see
["How the pipeline was run"](#how-the-pipeline-was-run-mirrors-20) step 5.
Availability/schedule data is still generated and stored in full (nothing is
deleted), it just doesn't factor into `compatibility_score` or `group_score`
right now. Academic per-topic strengths/weaknesses tracking was removed
entirely (not just excluded from scoring) — see "Known simplifications" below.

## The actual database

`schema.sql` + `build_database.py` turn `sample/*.json` into a real, normalized
SQLite database at `studymatch.db` (15 tables, ~900 rows, zero FK violations).
Rebuild it anytime with:

```
python build_database.py            # regenerates sample/*.json, then builds studymatch.db
python build_database.py --no-regen # builds studymatch.db from whatever's already in sample/
```

Open `studymatch.db` in [DB Browser for SQLite](https://sqlitebrowser.org/) or any
SQLite client. The ER diagram for this schema — plus the normalization decisions
behind it (why some things are wide columns and others are junction tables) — is in
[`ER_DIAGRAM.md`](ER_DIAGRAM.md).

### Adding real people alongside the fake ones

`student.source` (`'synthetic'` / `'real'`) lets real students coexist with the
fake ones in the same tables, distinguishably. Two ways to add one:

- **The webapp's survey** (below) — the normal path once real people are
  actually taking this. Signs them in AND places them in a group immediately.
- **`add_student.py`** (scripted/batch) — write raw data into a JSON file (see
  [`new_students.example.json`](new_students.example.json) for the shape) and run
  `python add_student.py new_students.example.json`. This **only inserts and
  recommends** — it assigns an archetype by nearest *existing* centroid (no
  re-clustering) and computes `pairwise_compatibility` against course-mates,
  but only *recommends* up to 3 under-capacity groups rather than actually
  joining one. Useful for bulk-loading people without triggering the live
  placement policy.

Both use [`matching_lib.py`](matching_lib.py) for scoring — same formula
everywhere, so the two paths can't silently drift apart.

Once someone is signed in (via either path), they're **permanent** — nothing
here deletes anyone automatically. `build_database.py`'s rebuild is destructive
(deletes and recreates `studymatch.db` from `sample/*.json` every run), so it
**refuses to run** once any real student exists — pass `--force` if you really
do want to blow the database away and start over from pure synthetic data. The
only way to remove someone (real *or* fake) is the admin page's delete button —
see below.

## The intake webapp (survey + admin)

```
pip install -r requirements.txt   # fastapi + uvicorn, if not already installed
python webapp.py
# -> http://localhost:8010/survey   the entry survey
# -> http://localhost:8010/admin    the admin view
```

Both pages talk directly to `studymatch.db` — no mock data, no separate store.

- **`/survey`** — name/year/gender/major, course, and the 14 personality
  traits (sliders), plus optional availability/academic fields. On submit:
  inserted as `source='real'`, scored against every course-mate, and placed
  into a group immediately per the policy below — never blocked on match
  quality. If the best available match is below `NOT_IDEAL_THRESHOLD` (65,
  reusing the same cutoff `group_feedback`'s `left_group` uses elsewhere),
  they're still signed in and grouped — just with a "this isn't a great fit"
  banner instead of a plain success one.
- **`/admin`** — every student, fake and real, searchable/filterable, each
  with a **Delete** button. Deleting removes them everywhere (personality,
  availability, academic profile, every `pairwise_compatibility` row
  involving them, group membership, chat messages, feedback) and recomputes
  or removes the group they were in — fake people can be deleted here too,
  same mechanism, no special case.

### The group-size remainder policy ([`group_placement.py`](group_placement.py))

Groups target exactly 5. Batch generation ([`generate_sample_data.py`](generate_sample_data.py))
only ever forms full 5-person groups and deliberately leaves a remainder
unassigned — that's why the fake population per course is sized as
**(a multiple of 5) + 2** (CMPSC 465 = 27, MATH 230 = 7): there are always
exactly 2 people per course with no group yet, ready to be completed by a
real survey respondent. Every time someone (real or, via `add_student.py`,
scripted) joins a course, the whole unassigned pool for that course is
re-evaluated fresh:

1. While **5 or more** are unassigned: peel off exactly-5 groups (best-pair
   seed, then greedy growth — same algorithm as the batch generator).
2. Whatever's left (0-4 people) is the remainder:
   - **0** — nothing to do.
   - **1 or 2** — each person individually joins whichever *existing*
     under-capacity group in the course scores best for them. If literally no
     group has room, they stay `pending` (a real edge case this doesn't try
     to solve further — flagged rather than papered over).
   - **3 or 4** — they become a brand-new (smaller) group together.

This is why the very first real survey respondent in a course typically gets
grouped immediately with the 2 fake "leftovers" (remainder becomes 3 → new
group), and the second respondent typically joins that same group (remainder
becomes 1 → joins the now under-capacity group from step 1).

## Viewing it as tables / rebuilding the browser yourself

`studymatch-data-browser.html` is a self-contained page (data baked in, no server, no
Claude) that lets you browse every file below as a searchable, sortable table. Rebuild
it anytime with:

```
python build_viewer.py            # regenerates sample/*.json, then rebuilds the HTML
python build_viewer.py --no-regen # rebuilds the HTML from whatever's already in sample/
```

Then just double-click `studymatch-data-browser.html` / open it in any browser. It only
reaches the network for the Google Fonts stylesheet — offline, it falls back to the
system sans/mono stack and still works. `viewer_template.html` is the page shell (all
the CSS/JS); `build_viewer.py` is the only thing that injects fresh data into it, at
the `__DATA_PLACEHOLDER__` marker.

## Reproducibility — same output every run

`generate_sample_data.py` seeds both `random` and `numpy` (`seed(42)`), and every place
that iterates a Python `set` sorts it first — sets otherwise iterate in an order that
depends on the interpreter's per-process hash seed, which would silently reshuffle tie
-breaks (e.g. *which* of two equally-compatible students fills a group's last seat)
between runs even with the RNG seeded. With that handled, **rerunning the script produces
byte-identical files**, every time, on any machine. That's deliberate — it's what makes
the dataset a stable target to build the schema/UI/algorithm against instead of a moving
one.

To get a *different* sample (e.g. to stress-test the UI with another population), either
change the seed value at the top of the script, or delete the two `seed(...)` lines for
true randomness each run — then note that group composition, chat text, and feedback
scores will all differ from what's checked in.

## A note on the chat and feedback data specifically

Both are the least "real" parts of this sample set, worth flagging before building on
them:

- **`course_chat_messages.json`** ([generator](generate_sample_data.py#L619)) — each
  message is `random sender × one of 6 fixed templates × one of the course's topics`.
  It's there to give the chat UI something to render and to represent the *shape* of
  that data (sender, type, upvotes, timestamp), not organic conversation — with only 6
  templates, several messages end up textually identical across different senders. Swap
  in real seed messages (or an LLM-written batch) before using it for anything but layout.
- **`group_feedback.json`** ([generator](generate_sample_data.py#L648)) — nothing here
  is "computed" from personality in a principled way. Each member's `satisfaction_score`
  is drawn from `Normal(mean = 2 + 3 × group_score/100, sd = 0.7)`, rounded and clipped
  to 1–5 — so it's a deliberately noisy proxy that merely *correlates* with the group's
  heuristic score, plus a small chance of `left_group` when `group_score < 65`.
  `would_match_again` is just `satisfaction ≥ 4 and not left`; `perceived_personality_fit`,
  `group_productivity`, and the two peer ratings are separate draws around the same
  baseline; `group_chat_activity` is uncorrelated random low/medium/high; every row shares
  one timestamp. This exists purely so the `group_feedback` **schema** is exercised end to
  end (and so you can eyeball "do higher-scoring groups roughly get better feedback?") —
  it is not a simulation of real student outcomes and carries no predictive signal beyond
  the correlation it was built with.

## How the pipeline was run (mirrors §20)

1. **Students & courses** — 27 students in CMPSC 465, 7 in MATH 230 (each a
   multiple of 5, plus 2 — see the remainder policy above). Matching is
   scoped per course throughout (Stage 1, §2).
2. **Personality survey** — each student's 14 trait scores are sampled from one of
   5 *hidden* generative subpopulations (used only to make the synthetic answers
   internally consistent, e.g. a "planner" type scores high on structure/preparation
   and low on talkativeness) with Gaussian noise. Ground-truth subpop labels are
   **not** written to output — real onboarding data wouldn't have them either.
3. **Archetypes** — `KMeans(k=5)` runs on the standardized 14-dim personality
   vectors in `personality_profiles.json`. Each cluster centroid is matched against
   a small rule bank (e.g. high leadership + high assertiveness + high competitiveness
   → "Study Captain") to name it — this is the §7 requirement that archetypes come
   *from* the data, not from an a-priori typology. Raw traits (not the archetype)
   drive all downstream matching.
4. **Availability** — each course has a shared "campus rhythm" of a handful of
   popular day/time windows (evenings after class, Sunday afternoon, etc.); each
   student draws 2–4 of those with small jitter, plus a 25% chance of one
   idiosyncratic block. This keeps schedules realistically clustered (so groups can
   actually form) while still leaving some students genuinely schedule-incompatible.
5. **Pairwise compatibility** (§9–11) — for every in-course pair:
   `compatibility_score = similarity`, scaled to 0–100, mean closeness across
   **all 14 personality traits** — no differences-rewarding term. `study_style`
   (schedule overlap, session length, location, online/in-person) is still
   computed and stored in `breakdown`, but carries zero weight — informational
   only. `schedule_compatible` / `weekly_overlap_minutes` are likewise still
   computed and stored per pair, but no longer exclude a pair from group
   formation (time isn't part of matching right now). There's no academic
   component anymore — see "Known simplifications."
6. **Group formation** (§13) — greedy: seed each new group from the best remaining
   compatible pair, grow to exactly 5 by adding whichever remaining student
   maximizes the group's average pairwise score, then run a bounded
   local-search pass that swaps members between groups whenever it raises
   both groups' combined `group_score`. Batch generation only ever produces
   full 5-person groups now — the 2-per-course remainder that's left over on
   purpose is completed later, live, by the webapp's survey (see "The
   group-size remainder policy" above).
7. **Group score** (§12): `group_score = avg_pairwise` (the group's mean pairwise
   similarity). `worst_pairwise` is still reported alongside it as a diagnostic,
   but no longer weighted in — no diversity/"balance" term either (that rewarded
   trait spread, i.e. differences, which matching no longer does).
8. **Recruiting recommendations** (§14) — every student left `looking_for_group`
   gets up to 3 ranked recommendations into existing under-capacity groups in their
   course, scored by average compatibility with current members.
9. **Feedback** (§16) — one row per (group, member) with satisfaction and related
   ratings sampled around a baseline that scales with `group_score` plus noise —
   intentionally imperfect, so it's usable to sanity-check whether the heuristic
   weights in step 5–7 actually predict good outcomes once you get real data.

## Known simplifications (flag before reusing past prototyping)

- Compatibility is personality-similarity-only by current decision, not because
  schedule signal is believed useless — `study_style` is kept computed and
  stored specifically so it's easy to re-weight back in later.
- Academic per-topic tracking (strong/weak topics, who can help who) was
  removed entirely — no `topic` table, no topic fields on `academic_profiles.json`.
  `academic_profile` now only carries `course_confidence`/`target_grade`. This
  was a deliberate simplification, not a data-quality issue: the old
  `can_help_with`/`needs_help_with` values were generated as exact duplicates
  of `strong_topics`/`weak_topics` (not sampled independently), so the signal
  wasn't adding anything a future rebuild couldn't reintroduce properly.
- Only 2 courses / 37 students — enough to exercise every stage of the pipeline, not
  a load-test.
- Gender is collected but genuinely unused in every scoring function, per §3.
- Because generation draws from one seeded, sequential random stream, removing
  the topic-sampling calls shifted every random draw after them — this
  snapshot's exact group compositions/scores differ from earlier ones checked
  into prior commits, even though the seed (42) hasn't changed. Reproducibility
  is still intact going forward: rerunning now reliably reproduces *this*
  snapshot.
